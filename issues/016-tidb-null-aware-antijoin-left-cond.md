# Candidate TiDB bug: `NOT IN` with a correlated condition on the outer row alone returns every outer row twice

Status: open, candidate (TiDB v7.5.1 and v8.5.3; MariaDB 10.11.14 and 11.8.9 and MySQL 9.7.4
are correct). Found by the
translation check of `bridge/campaign_mysql.py` on TiDB v8.5.3 (`.github/workflows/campaign.yml`,
`--tidb`; 13 pairs over seeds 1-40 and 131-170). Not reported upstream.

## Summary

```sql
CREATE TABLE t (a DECIMAL(10,2), b INT);
CREATE TABLE s (c INT, d INT);
INSERT INTO t VALUES (7.75, 1), (1.00, 2), (2.00, 3);

-- s is empty, so every NOT IN is TRUE: expected the 3 rows of t.  Returned: 6, each row twice.
SELECT t.a, t.b FROM t WHERE t.b NOT IN (SELECT s.c FROM s WHERE t.b <=> NULL AND s.d >= t.a);
```

The rows are duplicated whenever the subquery's `WHERE` has a condition that reads only the
outer row and can be NULL-safe-equal / IS NULL (`t.b <=> NULL`, `t.b IS NULL`, `t.a <=> NULL`).
`NOT (t.b IN (...))`, which is the same predicate, returns the right rows, as do `NOT EXISTS`
and the same query without that condition. A `WHERE` clause can only remove rows, so a query
over a table of 3 rows can never return 6.

## Variants

`data/tidb/not-in-correlated-empty.sql` (`t` has one row unless the tag says three):

| Query | Expected | TiDB v7.5.1, v8.5.3 | MariaDB 10.11.14, 11.8.9; MySQL 9.7.4 |
| --- | --- | --- | --- |
| A1 `t.b NOT IN (SELECT s.c FROM s WHERE t.b <=> NULL AND s.d >= t.a)` | 1 | **2** | 1 |
| A2 `NOT (t.b IN (...))`, the same subquery | 1 | 1 | 1 |
| B1 A1 without `t.b <=> NULL` | 1 | 1 | 1 |
| H2 `... WHERE t.b <=> NULL` alone | 1 | **2** | 1 |
| H3 `t.b IS NULL` instead of `t.b <=> NULL` | 1 | **2** | 1 |
| H4 `s.c <=> NULL` (the subquery's column) | 1 | 1 | 1 |
| H5 `t.b <=> 1` | 1 | 1 | 1 |
| H6 `t.a <=> NULL` (another outer column) | 1 | **2** | 1 |
| H7 `NOT EXISTS (... s.c = t.b AND t.b <=> NULL ...)` | 1 | 1 | 1 |
| H8 A1 where `s` has a row that does not match | 1 | **2** | 1 |
| H9 A1 on three rows | 3 | **6** | 3 |

## The plan

```
HashAgg      funcs:count(1)
└─HashJoin   Null-aware anti semi join, equal:[eq(t.b, s.c)], left cond:[nulleq(t.b, <nil>)],
             other cond:ge(cast(s.d, decimal(10,0) BINARY), t.a)
```

The condition on the outer row is turned into a `left cond` of the null-aware anti semi join.
Without it (B1) the plan is the same join with no `left cond`, and the result is right.
`NOT (... IN ...)` is planned as a `left outer semi join` followed by `not(...)`, and is right.
So the duplicate seems to come from the null-aware anti semi join when it has a `left cond`
that is false for the row: the row is emitted once because the `left cond` fails and once more
by the null-aware path. This reading comes from `EXPLAIN`, not from the source.

## How it was found

The translation check runs every query twice, as written and as re-printed by the bridge from
its term; the bridge prints `x NOT IN (q)` as `NOT (x IN (q))`. On TiDB the two returned
different rows for 13 queries, all with a correlated `NOT IN` whose subquery had a condition on
the outer row (`t1a.c4 <=> NULL`, `t2i45.c1 IS NULL AND t1b.c1 < 5`, ...), generated by the
rich generator. `bridge/reduce_mysql.py` reduced two of them to one row and an empty table;
the table above was written from those.

## Limitations

- TiDB v7.5.1 and v8.5.3 only (the two images tried).
- Upstream (web search, round 18; the tracker itself was not searched): the nearest report is
  TiDB issue 52902, "IndexHashJoin may produce redundant rows for anti semi left outer join",
  fixed in 2024 (PR 52908). It is about another join operator; the plan here is a
  `HashJoin` null-aware anti semi join, and v8.5.3 is newer than that fix. Not the same defect
  as far as the titles show.
- The cause is inferred from `EXPLAIN`.
- The campaign's other TiDB pairs (value rules, `cond->TRUE`) were not analysed in this round.
